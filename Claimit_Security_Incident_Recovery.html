Claimit — Security Incident & Recovery Plan

Prepared 15 September 2026  ·  Server 16.170.110.232  ·  MongoDB ransomware incident  ·  Status: live, unresolved
Read this first. Your production MongoDB was accessed by an attacker, every collection was deleted, and a ransom note was left behind. The application is still running but is serving an empty database. Do not restore the backup until the security hole is closed — restoring first means being wiped again within hours. The order of the steps in Part 3 is the whole point of this document.

Part 1 — What actually happened

The evidence

The password looks like it is protecting the database. It is protecting nothing.

mongod restarted Fri 11 Sep 06:30 UTC, on a box with 14 days uptime Not a reboot. Something restarted the database service mid-life. Likely the attack window.

How this attack works

This is an automated, untargeted attack that has hit tens of thousands of servers. Bots continuously scan the entire internet for MongoDB listening on port 27017. When they find one with no authentication, they connect as administrator, drop every database, and insert a ransom note. No password was guessed and no software vulnerability was exploited — the door was simply unlocked.

Unrelated: the missed ₹5,000 bill. A missed payment cannot cause this. No provider deletes your data and leaves a Bitcoin demand. The two are separate issues — but settle the bill anyway, because an instance suspended for non-payment would take your only backup with it.

Part 2 — Do not pay the ransom

In the overwhelming majority of these campaigns the bot never copies anything. It drops the databases and writes the note, because writing a note is cheap and copying gigabytes is not. There is usually nothing to buy back. Paying funds the operation and, in most documented cases, returns nothing.

Your recovery path is the backup already on the server: mongo_data_backup_20260817_0516.tar.gz, 262,758,785 bytes, dated 17 August 2026.

Be honest with yourself and your client about this: restoring that file returns you to 17 August. Every user, shop, advertisement, bill scan and review created between 17 August and today is permanently lost unless a newer copy exists somewhere else. That is roughly four weeks of growth.

Part 3 — Recovery sequence

Follow this order exactly. Each step assumes the previous one is finished.

1Get the backup off the server

Before anything else. If the box is terminated, re-attacked, or suspended for non-payment, this file is your only copy.

scp -i $key "${server}:/home/ubuntu/mongo_data_backup_20260817_0516.tar.gz" "F:\my_project_git\claimit_backup_20260817.tar.gz"

Verify the size is exactly 262,758,785 bytes:

Get-ChildItem "F:\my_project_git\claimit_backup_20260817.tar.gz" | Select-Object Name, Length

Then copy it to a second location — an external drive or cloud storage. One copy on one laptop is not a backup.

2Find out what format the backup is in

This determines which restore procedure applies. Run:

ssh -i $key $server "tar -tzf ~/mongo_data_backup_20260817_0516.tar.gz | head -20"
If you see…It is…Restore with…
dump/claimit_db/users.bson A mongodump archive mongorestore (Step 6a)
WiredTiger, collection-*.wt, _mdb_catalog.wt A raw copy of the data directory File-level replacement (Step 6b)

3Close the hole — security group

Confirmed on 15 September: security group sg-0b0b4ee04efc561a0 (launch-wizard-2), account Verso AI 951488807028, region eu-north-1. All five inbound rules are open to the entire internet:

Rule IDPortSourceVerdict
sgr-06f29c8ca820ba4ce27017 0.0.0.0/0 DELETE NOW — this is how they got in
sgr-00772e04d90b4adbf22 (SSH)0.0.0.0/0 Narrow to "My IP" — the whole internet can currently attempt to log in to your server
sgr-02fcd1412322471a180010.0.0.0/0 Keep for now — see the warning below

sgr-0eee4cdb347421ae080020.0.0.0/0 Close once you confirm nothing needs it (Step 8)

EC2 → Security Groups → sg-0b0b4ee04efc561a0 → Edit inbound rules. Delete the 27017 rule and change the SSH source to My IP. Save.

Do not delete the 8000 or 8001 rules today. There is no rule for port 80 or 443 at all, which means there is no nginx in front — every installed APK talks straight to 16.170.110.232:8001. Closing that port takes the app down for every user instantly. It gets fixed properly in Part 5, and that fix needs an app release first.
One clarification: the Compass connection labelled 13.53.194.96:27017 is only a stale display name — its actual URI is mongodb://admin:*****@16.170.110.232:27017. There is no second server. Only this one machine is affected.

4Bind MongoDB to localhost and turn on authentication

The security group is one lock. This is the second, and it is the one that matters if a rule is ever changed by mistake.

You already have an admin user — Compass authenticates with it. What you do not have is authorization: enabled, so MongoDB never checks. Creating more users without flipping that switch changes nothing. The switch is the fix.

First confirm which users exist and whether the password still works:

ssh -i $key $server

Then on the server:

mongosh --quiet --eval 'db.getSiblingDB("admin").system.users.find({},{user:1,roles:1}).toArray()'

If the existing admin account has full roles you can keep it and skip the next command. If you are not certain of its password, or it was created by the attacker, create a fresh one now, while auth is still off: 

mongosh --eval 'db.getSiblingDB("admin").createUser({user:"claimitroot", pwd:passwordPrompt(), roles:[{role:"userAdminAnyDatabase",db:"admin"},{role:"readWriteAnyDatabase",db:"admin"},{role:"backup",db:"admin"},{role:"restore",db:"admin"}]})'
Treat every existing MongoDB password as compromised. The attacker had administrative access with no authentication, which means they could read admin.system.users and create accounts of their own. Check that user list above for anything you do not recognise, and change the admin password regardless.

Then a separate, limited user that the application will use. This one can only touch claimit_db, so a leaked .env no longer means total loss:

mongosh --eval 'db.getSiblingDB("claimit_db").createUser({user:"claimit_app", pwd:passwordPrompt(), roles:[{role:"readWrite",db:"claimit_db"}]})'
passwordPrompt() asks for the password interactively so it never appears in your shell history. Use long random passwords — 24+ characters. Store them in a password manager, not in a text file.

Now edit the config:

sudo nano /etc/mongod.conf

Make these two sections read exactly:

net:
  port: 27017
  bindIp: 127.0.0.1

security:
  authorization: enabled

Restart and confirm:

sudo systemctl restart mongod
sleep 3
systemctl is-active mongod
sudo ss -lntp | grep 27017

That last line must now show 127.0.0.1:27017 and not 0.0.0.0:27017. Then prove the lock works — this must be rejected: 

mongosh --quiet --eval 'db.adminCommand({listDatabases:1})'

It should fail with an authorization error. If it still succeeds, auth did not take effect — stop and fix that before continuing.

From your laptop, Compass must now fail to connect to 13.53.194.96:27017 and 16.170.110.232:27017. To use Compass again, connect over an SSH tunnel: Advanced → SSH → Identity File (your .pem), user ubuntu, hostname localhost.

5Update the application's connection string

The app can no longer connect anonymously. Edit the .env in the folder the API actually runs from — confirmed as /home/ubuntu/claimit_local_production:

nano /home/ubuntu/claimit_local_production/.env

Set:

MONGODB_URL=mongodb://claimit_app:YOUR_PASSWORD@127.0.0.1:27017/claimit_db?authSource=claimit_db
DATABASE_NAME=claimit_db
chmod 600 /home/ubuntu/claimit_local_production/.env
Always 127.0.0.1, never the public IP — even from the server itself. Routing database traffic out to the internet and back is slower and means the connection only works while the port is open, which is exactly what you are closing.

6aRestore — if the backup is a mongodump archive

cd ~
mkdir -p restore_tmp
tar -xzf mongo_data_backup_20260817_0516.tar.gz -C restore_tmp
ls -R restore_tmp | head -30

Then restore, pointing at the folder that contains the .bson files:

mongorestore -u claimit_app -p 'YOUR_PASSWORD' --authenticationDatabase claimit_db --db claimit_db restore_tmp/dump/claimit_db

6bRestore — if the backup is a raw data directory

This takes MongoDB offline and overwrites its data files. Read the whole step before starting. Keep the current (empty) data directory rather than deleting it — it is your evidence and your undo. 
sudo systemctl stop mongod
sudo mv /var/lib/mongodb /var/lib/mongodb.attacked-20260915
sudo mkdir -p /var/lib/mongodb
sudo tar -xzf ~/mongo_data_backup_20260817_0516.tar.gz -C /var/lib/mongodb --strip-components=1
sudo chown -R mongodb:mongodb /var/lib/mongodb
sudo systemctl start mongod
sleep 3
systemctl is-active mongod

--strip-components=1 may need to be 0 depending on how the archive was created. The Step 2 listing tells you: if paths start with mongodb/, use 1; if they start with WiredTiger directly, use 0.

7Verify the data is back

mongosh -u claimit_app -p --authenticationDatabase claimit_db claimit_db --quiet --eval 'db.getCollectionNames()'
mongosh -u claimit_app -p --authenticationDatabase claimit_db claimit_db --quiet --eval 'db.users.countDocuments({})'
mongosh -u claimit_app -p --authenticationDatabase claimit_db claimit_db --quiet --eval 'db.shops.countDocuments({})'

You should see shops, ads, bill_history and reviews present again with real counts.

8Fix the process mess

Right now three uvicorn processes are running and two of them are orphans that PM2 does not manage:

PortPIDManaged byStatus
80003939920PM2 claimit-backendHealthy
8001445205Nobody — orphan started 12 Sep 04:26Serving your app

—2932442PM2 claimit-second-backendCrash loop, 158+ restarts
Do not kill PID 445205 until its replacement is ready. It is the only thing currently serving your app on port 8001. Its PM2 replacement cannot start — it is misconfigured.

claimit-second-backend fails with Could not import module "api.index". It was registered with a Vercel-style entry point that does not exist in this codebase; the correct one is app.main:app. Replace it: 

pm2 delete claimit-second-backend
cd /home/ubuntu/claimit_local_production
pm2 start venv/bin/uvicorn --name claimit-app-api -- app.main:app --host 0.0.0.0 --port 8001

That will fail to bind while the orphan holds the port, so stop the orphan in the same breath:

kill 445205
sleep 2
pm2 restart claimit-app-api
sleep 3
pm2 list
curl -s http://127.0.0.1:8001/health

Once everything is healthy, make it survive a reboot:

pm2 save
pm2 startup

Then run the command pm2 startup prints back to you.

Why 0.0.0.0 and not 127.0.0.1? Because every APK already installed on a user's phone has http://16.170.110.232:8001 compiled into it. Binding to localhost today would break every existing install instantly. Moving behind nginx is the correct fix, but it requires an app update first — see Part 5.

Identify port 8002 before deciding its fate:

ps -p 445202 -o pid,lstart,cmd --no-headers; sudo readlink /proc/445202/cwd

9Remove the ransom note — last, not first

Only after the restore is verified and you have kept a record of it:

mongosh -u claimitroot -p --authenticationDatabase admin --eval 'db.getSiblingDB("READ_ME_TO_RECOVER_YOUR_DATA").dropDatabase()'

Screenshot the note and record the Bitcoin address first. If you ever file a police report or a cyber-insurance claim, that is the evidence.

Part 4 — How the pieces connect, correctly

PHONE APP (Flutter) ADMIN WEB (React) | | | http://16.170.110.232:8001 | http://16.170.110.232:8000 v v +--------------------+ +--------------------+ | App API | | Web API | | uvicorn :8001 | | uvicorn :8000 | | claimit_local_ | | PM2 claimit- | | production | | backend | +--------------------+ +--------------------+ | \ | | \ | v v v +--------------+ +------------------+ | | MongoDB | | Amazon S3 |<-+ | 127.0.0.1 | | private bucket | | :27017 | | IAM role, no | | AUTH ON | | keys in .env | | LOCAL ONLY | +------------------+ +--------------+

The rules that keep it working

ComponentRuleWhy
MongoDB Bind 127.0.0.1 only. Authentication on. Never in a security group rule. This incident. The database has no business being reachable from outside the machine.
App user vs root user The API uses claimit_app, scoped to claimit_db only. A leaked .env then costs you one database, not the server.
S3 Block-all-public-access ON. Access via the EC2 IAM role, so AWS_ACCESS_KEY_ID stays empty. No long-lived keys exist to be stolen. Store the object key in Mongo and sign URLs on read.
Secrets Only in .env on the server, chmod 600. Never in app code, frontend code, or git. Anything in a shipped APK or a public repo is already public.
Processes Everything under PM2 with pm2 save. No manually started uvicorn. Orphans do not restart on reboot and nobody knows what config they hold — exactly the situation on port 8002 right now.

Part 5 — What is still wrong after recovery

Fixing the breach does not make this production-ready. These remain open, roughly in order of risk:

#ProblemConsequenceFix
1 No automated backups. The only backup is a manual tarball from 17 August. This incident costs four weeks of data. The next one costs however long since you last remembered. Nightly mongodump to S3 with a retention policy. See below.
2 Plain HTTP everywhere. No TLS. Every OTP, JWT and phone number travels in clear text over the network. Play Store's Data Safety form must declare "not encrypted in transit". Free DuckDNS subdomain plus sudo certbot --nginx -d name.duckdns.org. Costs time, not money.
3 Secrets committed to git, including claimit.pem and several .env files. Anyone with repository access has your server. The key is also sitting in your Downloads folder. Rotate the EC2 key pair, rotate every secret, purge from git history, move the .pem somewhere sensible.
4 API ports 8000/8001/8002 bound to 0.0.0.0. Bypasses nginx entirely. Internet scanners are already probing them — the logs show /mcp and /jsonrpc requests from unknown hosts. Put nginx in front, bind uvicorn to 127.0.0.1. Requires an app release first, because the current APK targets port 8001 directly.
5 No monitoring. Your database was empty for days and the first person to notice was you, by opening the app. An uptime check hitting /health, plus a daily job that alerts if users count drops.
6 Mystery process on port 8002; stage and several near-duplicate backend folders. Nobody knows which code is live. That is how an orphan ends up serving production. Identify, document, delete what is dead.
7 Twilio account restricted to 50 messages/day (error 63038) and blocked from provisioning numbers. Login OTP delivery is failing for real users — a separate live outage. Tracked separately: fix the Trust Hub profile, email compliance-review@twilio.com.

Nightly backup — the one that would have saved you

On the server, create /home/ubuntu/backup_mongo.sh:

#!/bin/bash
set -euo pipefail
STAMP=$(date +%Y%m%d_%H%M)
OUT="/home/ubuntu/backups/mongo_$STAMP"
mkdir -p "$OUT"
mongodump --uri="mongodb://claimit_app:YOUR_PASSWORD@127.0.0.1:27017/claimit_db?authSource=claimit_db" --out="$OUT"
tar -czf "$OUT.tar.gz" -C "$OUT" .
rm -rf "$OUT"
aws s3 cp "$OUT.tar.gz" "s3://YOUR-BUCKET/db-backups/"
find /home/ubuntu/backups -name '*.tar.gz' -mtime +14 -delete
chmod +x /home/ubuntu/backup_mongo.sh
chmod 600 /home/ubuntu/backup_mongo.sh
crontab -e

Add this line to run it at 02:00 server time every night:

0 2 * * * /home/ubuntu/backup_mongo.sh >> /home/ubuntu/backup.log 2>&1
A backup that has never been restored is not a backup. Once a month, extract the newest archive into a scratch database and count the documents. The first time you test a restore must not be the day you need it.

Part 6 — The part that is not technical

Your users collection held real people's phone numbers. Because MongoDB had no authentication and no audit log, you cannot prove whether that data was copied before it was deleted — and the tempusers / temproles artifacts suggest a dump was run. The responsible assumption is that it was taken.

Under India's Digital Personal Data Protection Act this is likely to carry a breach-notification obligation to both the affected users and the Data Protection Board, on a defined timeline.

I am not a lawyer and this is not legal advice. Engage someone who handles Indian data protection, today rather than next week — the clock on these obligations starts when you become aware, which was today. Tell your client now. Finding out from you is survivable; finding out from a regulator or a user is not.
