## 1. Project Overview

**Product Name:** Claimit
**Tagline:** *Every Bill is a Reward.*

### Problem Statement
Local businesses struggle to retain customers without expensive loyalty programs. Customers forget to return to shops they enjoyed. Advertisers have no cost-effective, hyperlocal ad platform to reach nearby shoppers. Sales affiliates (network marketers) have no structured digital tool to track shops they've onboarded. Claimit solves all three problems in one unified platform.

### Target Users

| Persona | Description | Pain Point |
|---|---|---|
| **Shop Owner** | Runs a local grocery, salon, gym, electronics store, etc. | Wants customer loyalty but can't afford complex CRM systems |
| **Advertiser / Brand** | A digital marketing agency or brand wanting to push hyperlocal ads | Needs a targeted ad placement platform for local discovery apps |
| **Sales Agent (Network Marketer)** | Person who onboards shops to Claimit | Needs a dashboard to manage their shop portfolio and track earnings |

### Core Value Proposition
Claimit is a three-sided loyalty + advertising + affiliate platform. Shops pay ₹999/year to list and offer cashback rewards to customers. Advertisers pay per-ad-slot to reach local buyers through Claimit's consumer app. Sales agents earn commissions by onboarding shops. All three portals share the same auth infrastructure but have separate dashboards and workflows.

### Monetization
- Shop annual subscription: ₹999/year
- Advertising revenue: ₹840–₹1400 per 7-day ad slot (Home Page Banner, Promo Reelz, Brand Deals, Nearby Deals)
- 1% shop incentive back to Claimit per transaction processed through the platform

## 3. Authentication & Registration Flow

All three portals share the same registration and OTP verification flow. The portal type is passed as a `role` param (advertiser / sales_agent / shop_owner) during registration so the backend tags the user correctly.

### 3.1 Shared Header (All Pages)
Every page — authenticated or not — renders the top navigation bar:
- **Left:** Claimit logo (yellow circle + wordmark "claimit")
- **Right nav links:** Help Centre · Support · Terms of Service · Privacy Policy
- **Auth buttons (unauthenticated):** Login-Ads | Sales Login | Shop Login
- **Auth state (authenticated):** Shows user avatar/initials + dropdown (Profile, Logout)

### 3.2 Registration Page

**Fields:**

| Field | Type | Required | Validation | Error |
|---|---|---|---|---|
| Phone Number | tel | Yes | 10-digit Indian mobile | "Enter a valid 10-digit number" |
| Email Address | email | Yes | RFC 5321 email format | "Enter a valid email address" |

**Flow:**
1. User lands on `/register?portal=ads` (or `sales`, `shop`)
2. Left panel: Illustrative image + motivational tagline (different per portal — see Section 5)
3. Right panel: "Register Your Account" form
4. On "Continue" click → POST `/api/auth/register` with `{phone, email, role}`
5. Backend: Check if email already exists → if yes, return 409 with "Account already exists, please login"
6. If new → create user record (`isVerified: false, isApproved: false`) → generate 6-digit OTP → store hashed OTP with 10-min TTL → send OTP via SMS + email
7. Redirect to OTP page
8. Bottom link: "Already have an account? **login**" → links to `/login?portal=<portal>`

**Backend Logic:**
```
POST /api/auth/register
Body: { phone: str, email: EmailStr, role: Enum['advertiser','sales_agent','shop_owner'] }
→ Check existing user by email
→ bcrypt.hash(otp, 12) → store in otp_store collection with expiry
→ Return 200: { message: "OTP sent to phone and email" }
→ On duplicate: 409: { detail: "Email already registered" }
```

### 3.3 OTP Verification Page

**UI:**
- 6 individual input boxes (auto-advance on digit entry, backspace goes back)
- "Didn't receive code? **Resend OTP**" link (available after 60s cooldown)
- "Verify OTP" button

**Flow:**
1. User enters 6 digits
2. POST `/api/auth/verify-otp` with `{email, otp}`
3. Backend: fetch hashed OTP → bcrypt.compare → if match and not expired → update user `isVerified: true`
4. If sales_agent or advertiser → skip to "Add Details" page or direct dashboard
5. If shop_owner → redirect to shop registration wizard

**Edge Cases:**
- Expired OTP (>10 min): 400 `{ detail: "OTP expired. Please request a new one." }`
- Wrong OTP: 400 `{ detail: "Invalid OTP." }` (max 5 attempts, then lock for 15 min)
- Resend: max 3 resends/hour per email, enforce via rate-limit middleware

### 3.4 Login Flow

**Fields:** Phone Number or Email + (implicit — no password shown in designs; OTP-based login)
- Each login attempt triggers a fresh OTP to the registered phone + email
- On successful OTP verify → issue JWT access token (15 min) + refresh token (7 days, httpOnly cookie)
- Role decoded from JWT → frontend redirects to appropriate dashboard

```
POST /api/auth/login
Body: { email: str }
→ Lookup user → if not found: 404
→ if isVerified: false → 403 "Please verify your email first"
→ if isApproved: false (shop_owner) → 403 "Account pending approval"
→ Generate OTP → send → 200 "OTP sent"

POST /api/auth/verify-login-otp
Body: { email: str, otp: str }
→ Verify OTP → issue accessToken + refreshToken
→ Return: { accessToken, role, userId }
```

### 3.5 Token Strategy
- Access Token: JWT, 15-min expiry, payload: `{ userId, role, email }`
- Refresh Token: 7-day expiry, stored in httpOnly cookie
- All protected routes validate Bearer token via `Depends(get_current_user)` in FastAPI
- Token refresh endpoint: `POST /api/auth/refresh`

## 4. Onboarding Flow

### Advertiser (Login-Ads)
After OTP verify → lands directly on Advertiser Dashboard with "Get Started" empty state showing "Post Advertising" card → click "Get Started" → redirects to "Create Ad" flow (Step 1: Choose Ad Type).

- Your Name (text, required)
- Address (text, required)
- Pincode (6-digit, required)
- Geo Location → "Use my current location" button (calls browser Geolocation API)
- Continue → lands on Sales Dashboard

### Shop Owner (Shop Login)
After OTP verify → "Choose The Services" screen → one option card: "Add Shop or Business" → "Get Started" button → Shop Registration Wizard (multi-step).

## 7. AI Features (Suggested)

While the current designs don't show explicit AI features, the following AI layers are recommended:

### 7.1 Smart Ad Targeting
- **What:** AI ranks nearby shops/brands in consumer app feed based on user history + location
- **Model:** Collaborative filtering on MongoDB transaction data
- **Input:** User location, purchase history, category preferences
- **Output:** Ranked list of deals shown in the consumer app

### 7.2 Offer Optimization Suggestions
- **What:** When Shop Owner is on Offer Management, AI suggests optimal discount %
- **Model:** Historical data: shops with 20% discount saw 34% more transactions this week
- **Input:** Shop category, local competitor discounts, historical redemption rate
- **Output:** "Shops like yours perform best at 20% — try it!" recommendation card

### 7.3 Ad Copy Assistant (Advertiser Portal)
- **What:** On "Add Details" page, a "Generate with AI" button auto-fills Ad Title and Description
- **Model:** Anthropic Claude API (claude-sonnet-4-6)
- **Input:** Ad type + pincode + business category
- **Output:** Suggested title + description, user can edit

### 7.4 Review Sentiment Analysis
- **What:** Shop owner dashboard shows sentiment score per review (Positive / Neutral / Negative badge)
- **Model:** Lightweight NLP classifier (VADER or Hugging Face)
- **Input:** Review text
- **Output:** Sentiment label + score

### 7.5 Fraud Detection
- **What:** Flag suspicious bill scan patterns (same user scanning same bill multiple times)
- **Model:** Rule-based anomaly detection + ML classifier
- **Input:** transaction.userId, transaction.shopId, transaction.timestamp, transaction.billAmount
- **Output:** Flag transaction for admin review

## 10. Data Flow Diagrams

### Flow 1: User Registration & OTP Verification

```mermaid
sequenceDiagram
  actor User
  participant Frontend
  participant FastAPI
  participant MongoDB
  participant EmailSMS

  User->>Frontend: Fill phone + email, click Continue
  Frontend->>FastAPI: POST /api/auth/register {phone, email, role}
  FastAPI->>MongoDB: Check if email exists
  MongoDB-->>FastAPI: Not found
  FastAPI->>MongoDB: Insert user {isVerified:false}
  FastAPI->>FastAPI: Generate 6-digit OTP, bcrypt hash
  FastAPI->>MongoDB: Insert otp_store {otpHash, expiresAt: +10min}
  FastAPI->>EmailSMS: Send OTP via email + SMS
  FastAPI-->>Frontend: 200 "OTP sent"
  Frontend->>Frontend: Redirect to /verify-otp
  User->>Frontend: Enter 6-digit OTP
  Frontend->>FastAPI: POST /api/auth/verify-otp {email, otp}
  FastAPI->>MongoDB: Fetch otp_store by email
  FastAPI->>FastAPI: bcrypt.compare(otp, otpHash)
  FastAPI->>MongoDB: Update user isVerified:true
  FastAPI-->>Frontend: 200 {accessToken, role}
  Frontend->>Frontend: Redirect to portal dashboard
```

## 12. Security Considerations

| Area | Implementation |
|---|---|
| OTP Storage | bcrypt hash (rounds=12), TTL index auto-delete after 10 min |
| OTP Attempts | Max 5 wrong attempts → lock OTP for 15 min, return 429 |
| JWT Access Token | 15-min expiry, HS256, payload: {userId, role, email} |
| JWT Refresh Token | 7-day expiry, stored as httpOnly cookie, hashed in DB |
| Password (Admin) | bcrypt hash (rounds=12), never plaintext |
| RBAC | FastAPI Depends() guards: `get_current_user` + role check on every protected route |
| Rate Limiting | slowapi (FastAPI): /register: 3/hour/IP; /login: 5/15min/IP; /resend-otp: 3/hour/email |
| Input Sanitization | Pydantic v2 validators on all request bodies (EmailStr, constr, regex patterns) |
| File Upload | Max 50MB ads creative, 5MB photos; validate MIME type server-side (not just extension) |
| CORS | Allow only registered frontend origin (Vite dev + production domain) |
| HTTPS | Enforce in production; 301 redirect HTTP → HTTPS |
| Admin 2FA | TOTP via pyotp (Google Authenticator compatible) — recommended for all admin accounts |
| Audit Logging | Every admin action → insert to audit_logs collection |
| XSS | React auto-escapes; no dangerouslySetInnerHTML used |
| MongoDB Injection | Motor/Beanie with Pydantic models prevents query injection |

## 13. Edge Cases & Validations

| Scenario | Handling |
|---|---|
| Empty required fields | Inline red error under field; button remains disabled |
| Invalid email format | "Enter a valid email address" — client-side + server-side |
| Duplicate email registration | 409: "An account with this email already exists. Please login." |
| OTP expired | 410: "OTP has expired. Click Resend OTP." — old OTP deleted from DB |
| Wrong OTP (< 5 attempts) | 400: "Invalid OTP. X attempts remaining." |
| Wrong OTP (5th attempt) | 429: "Too many attempts. Please request a new OTP in 15 minutes." |
| Login before OTP verify | 403: "Please verify your OTP first." |
| Shop login before admin approval | 403: "Your shop registration is under review. We'll notify you once approved." |
| Resend OTP limit (>3/hour) | 429: "Too many resend attempts. Try again in 1 hour." |
| Ad creative > 50MB | Client-side: "File exceeds 50MB limit" before upload |
| Invalid pincode | "Enter a valid 6-digit pincode" — regex: /^\d{6}$/ |
| Schedule date > 10 days | Date picker disables those dates; API validates: 400 if exceeded |
| Schedule date in the past | Date picker disables past dates |
| Accessing other user's resources | 403: "Forbidden" — all queries filter by userId from JWT |
| Expired JWT on protected route | 401 → frontend catches → attempts refresh → if refresh expired → redirect to login |
| File wrong format (not JPG/PNG/MP4) | "Only JPG, PNG, and MP4 files are supported" |
| Network failure during payment | Show "Payment failed. Please try again." — do not create ad record until payment confirmed |
| Admin approves already-active shop | 409: "Shop is already active" |
| DB connection failure | 503: "Service temporarily unavailable. Please try again later." |
| Concurrent OTP requests | Last OTP wins; previous OTP invalidated on new generation |
