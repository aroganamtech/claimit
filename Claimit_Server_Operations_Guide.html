Status: the database emergency is over. Data restored, the way in is closed, automatic backups are running. What remains is ordinary hardening — important, but no longer an open door.

1. What happened, in one paragraph

On 11 September a bot found MongoDB on port 27017, open to the whole internet and not checking passwords. It deleted every collection and left a database called READ_ME_TO_RECOVER_YOUR_DATA demanding 0.0065 bitcoin. No ransom was paid. The database was rebuilt from a 17 August backup that happened to be sitting on the server. Everything created between 17 August and 15 September was lost.

The cause was two mistakes that only mattered together: port 27017 was open to 0.0.0.0/0, and although an admin user existed, authorization was never switched on in mongod.conf — so MongoDB accepted a password when offered and shrugged when one wasn't. Both are now fixed.

4. Day-to-day commands

Start every session with these two lines:

$key = "C:\Users\sk764\Downloads\claimit.pem"
$server = "ubuntu@16.170.110.232"
Use systemd. Never PM2. PM2 was removed on 18 September and pm2-ubuntu.service is disabled. For months both systemd AND PM2 were starting the same two apps: at every boot they raced for ports 8001 and 8002, the loser crash-looped hundreds of times, and the survivors looked like untracked "orphan" processes. Every mystery outage that week traced back to it. Adding anything back under PM2 recreates the whole problem.

Is everything alive?

ssh -i $key $server "systemctl is-active claimit claimit_web mongod"
curl.exe -s -m 10 "http://16.170.110.232:8001/health"

And the check that catches duplicates — this must print exactly two lines:

ssh -i $key $server "ps aux | grep uvicorn | grep -v grep"

Restart a backend

ssh -i $key $server "sudo systemctl restart claimit; sleep 6; systemctl is-active claimit"
ssh -i $key $server "sudo systemctl restart claimit_web; sleep 6; systemctl is-active claimit_web"

Read the logs

ssh -i $key $server "journalctl -u claimit -n 50 --no-pager"
ssh -i $key $server "journalctl -u claimit_web -n 50 --no-pager"
ssh -i $key $server "systemctl status claimit --no-pager"

Deploy a changed file

scp -i $key "F:\my_project_git\claimit\fastapi\backend\app\routes\auth.py" "${server}:/home/ubuntu/claimit_local_production/app/routes/auth.py"
ssh -i $key $server "sudo systemctl restart claimit; sleep 6; systemctl is-active claimit"
The remote path mirrors the local path under the backend folder. Note the app backend deploys to claimit_local_production and the admin backend to claimit_web_local_backend — not the *_ec2 folders, which are stale copies from June.

Run a backup right now

ssh -i $key $server "bash ~/backup_mongo.sh"

With a test-restore to prove the archive actually works:

ssh -i $key $server "bash ~/backup_mongo.sh --verify"

List backups and copy the newest to your PC

ssh -i $key $server "ls -lht ~/backups/ | head"
scp -i $key "${server}:/home/ubuntu/backups/mongo_YYYYMMDD_HHMM.tar.gz" "F:\my_project_git\"

Count your data

ssh -i $key $server "URI=$(grep -E '^MONGODB_URL=' /home/ubuntu/claimit_local_production/.env | cut -d= -f2-); mongosh \"$URI\" --quiet --eval 'const d=db.getSiblingDB(\"claimit_db\"); print(d.users.countDocuments({}) + \" users, \" + d.shops.countDocuments({}) + \" shops\")'"

Read the database password

ssh -i $key $server "grep MONGODB_URL /home/ubuntu/claimit_local_production/.env"
The password is the part between admin: and @. Put it in a password manager. Do not paste the output of this command into a chat, an email or a screenshot.

Rotate the password

ssh -i $key $server "bash ~/rotate_db_password.sh"

Then read the new one with the command above and save it.

Connect with MongoDB Compass

Never reopen port 27017. Use an SSH tunnel instead — Compass supports this natively:

  1. New connection → URI: mongodb://admin:<password>@localhost:27017/?authSource=admin
  2. Advanced Connection Options → Proxy/SSH → SSH with Identity File
  3. SSH Hostname: 16.170.110.232, Username: ubuntu, Identity File: your claimit.pem

5. If the data disappears again

Restore the newest backup. This is mongorestore, not the raw file swap used on 15 September — safer, and it doesn't stop MongoDB.

ssh -i $key $server "ls -t ~/backups/*.tar.gz | head -1"
ssh -i $key $server "cd ~ && rm -rf restore_tmp && mkdir restore_tmp && tar -xzf $(ls -t ~/backups/*.tar.gz | head -1) -C restore_tmp && ls -R restore_tmp | head -20"

Then restore, pointing at the folder holding the .bson files:

ssh -i $key $server "URI=$(grep -E '^MONGODB_URL=' /home/ubuntu/claimit_local_production/.env | cut -d= -f2-); mongorestore --uri=\"$URI\" --drop ~/restore_tmp/mongo_*/"
--drop replaces existing collections. Only use it when the current data is known-bad. If you are unsure, restore into a scratch database first by adding --nsFrom='claimit_db.*' --nsTo='claimit_db_check.*' and inspect it before committing.

7. The rule that matters most

Never open port 27017 again. Not for Compass, not "just for five minutes", not for a colleague. The SSH tunnel in section 4 does the same job with none of the risk. Every MongoDB ransom incident starts with someone opening that port temporarily.

Two habits worth keeping:

  • Test a restore once a month. Run bash ~/backup_mongo.sh --verify. A backup nobody has restored is a guess, not a backup.
  • Check the backup log occasionally. ssh -i $key $server "tail -20 ~/backup.log" — a cron job that quietly stopped working is worse than no cron job, because you think you are covered.
